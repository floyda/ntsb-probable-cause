# S2.5 — The recorder: implementation plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Spec:** docs/specs/2026-09-22-s25-recorder-design.md

**Goal:** A nightly job that polls every ongoing Part 91 investigation, records when each
docket document and each structured evidence field first appears, and stores the
preliminary narrative — in a SQLite store, on AWS, with Andy's Mac as a bridge.

**Architecture:** Three new packages over the existing library: `store/` (the only code that
touches SQLite), `recorder/` (the nightly logic, every network and clock call injected),
`apps/recorder/` (the `ntsb-record run` entrypoint). The S2 docket client fetches listings
with its cache off; the existing API client fetches event months and gains one method for the
change feed. Every "when" is an interval between two run ids. Specification:
`docs/specs/2026-09-22-s25-recorder-design.md` (Approved 2026-09-22); decisions 0060–0071.

**Tech Stack:** Python 3.14, `sqlite3` (standard library), pydantic, httpx + respx (tests),
`boto3` behind an `aws` extra for the S3 sync, AWS CDK (Python) under `infra/`, Docker.

## Global Constraints

Every task's requirements include these. Copied from the specification and CLAUDE.md.

- `make check` (ruff format, ruff check, import-linter, deptry, vulture, `mypy --strict`,
  pytest with `--disable-socket` and `--cov-fail-under=90`) must pass after every task.
- The docket client's rate floor is one request every 2.0 seconds to `data.ntsb.gov`; the API
  client's is 30 requests a minute. Tests inject `sleep`, never set the rate to 0.
- No document is ever downloaded (0061). The recorder calls `DocketClient(cache_dir=None)` (0066).
- Every record passes through `split_record`; only `Evidence` is ever written (0064 rule 3).
  No synthesis or verdict string may appear in the SQLite file, checked as bytes.
- Every "when" is a pair of run ids: last seen absent, first seen present (spec §3). Never a
  single guessed date. All timestamps UTC ISO-8601.
- Watched = `mode` aviation, `completionStatus == "Ongoing"`, regulation `"091"` or empty, or
  within 30 days of leaving `Ongoing` (0067, 0064). Never `!= "Completed"`.
- Open-split text (titles, narratives, pages) lives only in the store. Scripts print counts
  only: no case numbers, no titles, no text (0024).
- Every script in `scripts/` opens with a `Status` docstring block (0059): kind, what it
  produced, what has since changed.
- Nothing under `data/` is committed. The store's default path is `data/recorder.sqlite`.
- Logs never contain case text. One line per case per side, one per step, the summary last.
- Plans live in `docs/plans/`; tick tasks in the same commit as their code; log deviations in
  the "Deviations" section at the end of this file.
- Commit messages: `S2.5: <what>`; end with the attribution lines the session reminder gives.
- Simplified technical English in the runbook, with a glossary; clinical tone everywhere.

```python
_INFO_BLOCK = re.compile(r"<h2><b>Docket Information</b></h2>")
_CREATION = re.compile(r"<b>Creation Date:</b>\s*([^<]*)<")
_MODIFIED = re.compile(r"<b>Last Modified:</b>\s*([^<]*)<")
_RELEASE = re.compile(r"Public Release Date &(?:amp;)? Time:\s*([^<]*)<")


class DocketInfo(BaseModel):
    """The docket-level dates the page prints, as printed. Not per document (spec §6.2)."""

    model_config = ConfigDict(frozen=True)
    creation_date: str | None
    last_modified: str | None
    release_date: str | None


def _info(page: str) -> DocketInfo | None:
    if not _INFO_BLOCK.search(page):
        return None

    def first(pattern: re.Pattern[str]) -> str | None:
        match = pattern.search(page)
        value = html.unescape(match.group(1)).strip() if match else ""
        return value or None

    return DocketInfo(
        creation_date=first(_CREATION), last_modified=first(_MODIFIED), release_date=first(_RELEASE)
    )
```

`failed` with `outcome_for_error(str(error))` as the reason; `is_not_released(page)` (checked
on the raw page, before `parse_listing` runs) -> `no-docket`; `parse_listing` raising
`DocketError` (a declared/parsed count mismatch) -> `failed: count-mismatch`; `listing.info is
None` -> `failed: no-info-block` (also catches a page with no count and no "not released"
sentence, so a layout change stays visible); any entry with no parseable `ID=` in its href ->
`failed: entry-without-id`, nothing diffed; otherwise `read`, or `empty` if there are no
entries; two entries sharing one document id (`failed: duplicate-id`, Task 8 fix round 1,

`last_docket_run` (it is itself an observation of absence, spec §3) but never touches a
document; `failed` updates nothing. The page is gzipped (`gzip.compress(page.encode())`),
hashed (`sha256` of the raw page), and stored when `has_page` is false -- for every outcome
where a page was actually received (`read`, `empty`, `no-docket`, and the four `failed`
reasons above), never for a fetch error. `absent_run` for a document appearing this run --
whether it has never been seen before or is returning after having disappeared -- is always

that did not see it, which is what spec §3's "last seen absent" means).

each `(title, pages)` key, `min(disappeared count, appeared count)` (Task 8 fix round 1,

- **2026-09-23 (pre-deploy fix round, item A -- the outage budget, five corrections)**. Andy's
  final re-review found the whole-branch review's outage budget (0025 above) would not
  actually have kept a real hung API run inside the container's 90-minute limit, and fixed all
  five gaps before migration 3 shipped:
  1. **The change feed was completely ungated.** It hits the same API host
     `cases_by_date_range` does, so a hung API could exhaust the case side's own budget and
     then the UNGATED feed call would add its own full retry worst case on top -- roughly 96
     minutes total against a 90-minute container, by the reviewer's own walked-through
     arithmetic. `_feed_side` (`recorder/run.py`) is now skipped -- one failure, one log line,
     `cases_modified` never called -- when the run deadline has already passed OR the case-side
     circuit breaker has already tripped (the docket side's own breaker does NOT gate it: a
     docket outage says nothing about the API host).
  2. **`RUN_DEADLINE_MINUTES` was 75 against a wrong "~2.5 minutes" estimate** of one request's
     own worst case. The real figure -- 5 retried attempts, each up to the client's own
     120-second httpx timeout, plus backoff (2+4+8+16=30s), plus rate-limit gaps -- is about
     10.7 minutes for the API and 10.5 for the docket client. The constant is now 65, with the
     full arithmetic in its own comment: 65 (budget) + 10.7 (one more request's worst case
     already in flight when the deadline is checked) + about 10 (store push and task
     startup/shutdown overhead the runbook budgets) = 85.7 minutes, under the scheduler's 90.
  3. **The deadline was checked only once per MONTH**, so a single hung, multi-page month could
     still run every remaining page of itself past the deadline before the next check.
     `_observe_month_streaming` now checks it before every PAGE too (`api.cases_by_date_range`'s
     generator is driven with an explicit `next()` so the check can sit between pages, not only
     around the whole call); a month cut short this way is `errored=True`, exactly like a
     mid-month `ApiError` -- no `run_months` row, no "not returned" marking.
  4. **The docket circuit breaker counted every kind of failure**, including fast PARSE
     failures (`no-info-block`, `count-mismatch`, `entry-without-id`, `duplicate-id`) that mean
     the site answered and only its page content was unusual -- a real layout-change night
     could then trip the breaker after ten pages and stop storing the raw pages spec §6.4 needs
     precisely to diagnose that change. `_is_docket_outage_reason` now decides: only a reason
     ending `-after-retries` or starting `fetch-failed:` (both mean every retry was exhausted
     without an answer) counts toward the breaker, or resets it; everything else -- a parse
     failure, or a FAST non-retried status such as a plain `http-404` for one case that
     genuinely has no docket -- is treated the same as a real success (counted as an ordinary
     failure in the summary, but never trips the breaker, and resets any in-progress streak,
     since the site did answer).
  5. **Tests replaced/added, elapsed-clock driven, not call-counted** (a fresh `_ElapsedClock`
     test helper in `tests/test_recorder_run.py`, advanced only by the injected `sleep`
     callback and by respx `side_effect`s modelling one request's own elapsed time -- never by
     counting how many times `now()` happens to be called, so a refactor that changes
     `run_night`'s internal call sequence cannot break these silently):
     `test_deadline_trips_mid_docket_loop_and_the_run_still_finishes` (rewritten),
     `test_case_side_month_deadline_skips_remaining_months_and_gates_the_feed` (new -- also
     covers the previously-uncovered per-month deadline branch),
     `test_feed_skipped_after_case_side_breaker_trips` (new),
     `test_page_level_deadline_stops_before_the_next_page` (new),
     `test_docket_breaker_not_tripped_by_parse_failures_all_pages_stored` (new). The two
     existing breaker tests (`test_docket_circuit_breaker_trips_after_ten_consecutive_failures`,
     `test_month_circuit_breaker_trips_and_the_docket_side_still_runs`) already used a FIXED
     clock (never advancing, so the deadline could never interfere), which is not the fragile

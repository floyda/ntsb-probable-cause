# Runbook — the recorder's Mac bridge

*Read this before you start the bridge. It has one decision only you can make (stage 2), and
one fact that matters if a night ever goes wrong (the box after stage 4).*

**What this sets up.** The recorder (`ntsb-record run`) needs to run once every night,
starting from the day it merges. The AWS pieces that will eventually run it
(`docs/runbooks/recorder-deploy.md`) are not built yet. Until they are, your Mac runs the same
command every night at 03:00, through a macOS feature called `launchd` — the "bridge" the
specification names in §9.3. Bridge and cloud run the exact same code; only where the file
lives changes, and that is one setting (`NTSB_STORE`).

Every term in **bold** the first time it appears is in the glossary at the end.

---

## Stage 1 — What runs, and from where

Three pieces, already written:

1. **`scripts/recorder_bridge.sh`** — a small wrapper. It reads the NTSB API key from
   `pass` (your password store), sets the data directory, runs `ntsb-record run`, and writes
   one line to the log for every outcome. You do not edit this file to use it.
2. **A `launchd` job** (stage 5) — the alarm clock. It runs the wrapper every night.
3. **The recorder's code** — the actual `ntsb-record run` program.

**Which copy of the code the bridge runs.** This stage (S2.5) is built on a branch,
`s25-recorder`, checked out in its own folder so it does not disturb your main checkout:

```
/Users/floyda/Workspace/ntsb-demo-agent/ntsb-probable-cause/.claude/worktrees/s25-recorder
```

This kind of folder is called a **worktree** — a second, independent copy of the same
repository, checked out to a different branch, sharing the same git history. Point the bridge
at this worktree for now. **Once this stage is merged to `main`**, switch the bridge to your
main checkout instead:

```
/Users/floyda/Workspace/ntsb-demo-agent/ntsb-probable-cause
```

(stage 7 below shows the one-line change). Either way, **the store file and the log always
live in the main checkout's `data/` folder** — `scripts/recorder_bridge.sh` sets that on
purpose, so switching which code runs the recorder never moves or splits the data.

---

## Stage 2 — Your decision: how long the key stays unlocked

`pass` encrypts the NTSB API key with GPG. Reading it back needs a passphrase, checked by a
small program called **`pinentry`** — on your Mac, `pinentry-mac`, which can remember the
passphrase for a while so you are not asked every time. Yours is set to remember it for 24
hours (`default-cache-ttl 86400`).

**The problem.** The recorder runs at 03:00, while you are asleep. If the passphrase is not
already cached at that moment, `pass show api/ntsb` pops a dialog on your screen and waits for
you to type it — nobody is there, so the run either stalls or fails with no key. The wrapper
script protects against the *stalling* half of this: it gives `pass` 60 seconds, then gives up
and logs `NTSB key unavailable` rather than hanging forever. It cannot make the key appear.

**Your choice, not a setting in the code:**

- **Tick "Save in Keychain"** the next time the `pinentry-mac` dialog appears (for example,
  right after you install the bridge and run it once by hand in stage 6). The passphrase is
  then always available, and every night succeeds.
- **Or do nothing**, and accept that some nights will fail with "NTSB key unavailable" — most
  often the first night after your Mac restarts, since that clears the cache. This is safe:
  spec §3 promises that a missed night only *widens the interval* the next run measures against
  (it never invents a false date), so a run that does not happen is never a wrong answer, only
  a later one.

Either is fine. Pick whichever matches how much you want to think about this.

---

## Stage 3 — `launchd` runs in your Mac's local time

The 03:00 the specification gives for the AWS schedule (§9.2) is 03:00 **UTC**. `launchd`
does not work in UTC — it uses your Mac's **local** clock. London is UTC in winter and one hour
ahead (British Summer Time) in summer, so "03:00 local" is 03:00 UTC for part of the year and
02:00 UTC for the rest. This does not need fixing: the recorder never depends on the exact
hour, only on running roughly once a night (spec §3's "interval," not a fixed timestamp), so
the one-hour seasonal drift changes nothing about what it measures.

---

## Stage 4 — A missed night is a wider gap, never a wrong answer

Two ways a night can be missed, and what each one means:

| Your Mac was... | What happens | Effect |
|---|---|---|
| Asleep | `launchd`'s `StartCalendarInterval` runs the job as soon as the Mac wakes | The run just happens a bit late; nothing is lost |
| Fully off | The 03:00 trigger never fires | That night is skipped entirely |

Both are fine, for the same reason as stage 2: a skipped night only widens the interval
between two observations, and the recorder never claims a date it does not have.

> **One fact worth holding onto, because it decides how worried to be when a night fails.**
> Spec §9.1 says "if the task dies mid-run, tonight's rows are lost." **That sentence is true
> for AWS, but not for your Mac while the bridge runs it.** On AWS, the store lives in S3 and
> is downloaded to a temporary copy for the night; if the task dies, that copy is thrown away
> and nothing it wrote survives. On your Mac, `NTSB_STORE` points straight at
> `data/recorder.sqlite` — **that file *is* the store**, not a temporary copy of it. Every
> single write the recorder makes is its own database transaction (`store/db.py`), committed
> to disk immediately. So if a bridge run dies halfway through — the Mac loses power, you close
> the lid, anything — everything it had already written up to that point is real,
> already-saved data. The only thing left unfinished is that one night's own summary row
> (`runs`), which nothing reads as a valid night anyway. Losing data is an AWS-only risk;
> on the bridge, a crash costs you nothing you did not already have.

## Stage 5 — Install the `launchd` job

**First, find where your tools live**, because `launchd` jobs run with almost no `PATH` set —
they do not automatically see what your Terminal sees:

```
which uv
which pass
which perl
```

Typical Homebrew locations are `/opt/homebrew/bin` (Apple Silicon) or `/usr/local/bin`
(Intel); `perl` is normally already at `/usr/bin/perl`. Use what `which` actually printed, not
the guess below, when you fill in the plist.

**Create the plist** (a **plist** — "property list" — is the XML file `launchd` reads to
know what to run and when) at
`~/Library/LaunchAgents/dev.floyda.ntsb-record.plist`:

```xml
<?xml version="1.0" encoding="UTF-8"?>
<!DOCTYPE plist PUBLIC "-//Apple//DTD PLIST 1.0//EN" "http://www.apple.com/DTDs/PropertyList-1.0.dtd">
<plist version="1.0">
<dict>
    <key>Label</key>
    <string>dev.floyda.ntsb-record</string>

    <!-- Argument 1 is the wrapper script; argument 2 is the code directory it runs FROM
         (stage 1 -- the worktree for now, the main checkout after the merge). -->
    <key>ProgramArguments</key>
    <array>
        <string>/Users/floyda/Workspace/ntsb-demo-agent/ntsb-probable-cause/.claude/worktrees/s25-recorder/scripts/recorder_bridge.sh</string>
        <string>/Users/floyda/Workspace/ntsb-demo-agent/ntsb-probable-cause/.claude/worktrees/s25-recorder</string>
    </array>

    <!-- 03:00 in whatever your Mac's local time zone currently is (stage 3). -->
    <key>StartCalendarInterval</key>
    <dict>
        <key>Hour</key>
        <integer>3</integer>
        <key>Minute</key>
        <integer>0</integer>
    </dict>

    <!-- launchd's own minimal PATH does not include Homebrew or uv. Replace this with what
         `which uv`/`which pass`/`which perl` printed above. -->
    <key>EnvironmentVariables</key>
    <dict>
        <key>PATH</key>
        <string>/opt/homebrew/bin:/usr/local/bin:/usr/bin:/bin</string>
    </dict>

    <!-- Belt and braces: the wrapper already appends everything to this file itself, but
         anything printed before it gets that far (for example, a permission error starting
         the script) is caught here too, in the same file. -->
    <key>StandardOutPath</key>
    <string>/Users/floyda/Workspace/ntsb-demo-agent/ntsb-probable-cause/data/recorder.log</string>
    <key>StandardErrorPath</key>
    <string>/Users/floyda/Workspace/ntsb-demo-agent/ntsb-probable-cause/data/recorder.log</string>
</dict>
</plist>
```

**Load it:**

```
launchctl bootstrap gui/$(id -u) ~/Library/LaunchAgents/dev.floyda.ntsb-record.plist
```

(On an older macOS where `bootstrap` is unavailable, use
`launchctl load ~/Library/LaunchAgents/dev.floyda.ntsb-record.plist` instead — both do the
same thing.)

## Stage 6 — Run it once by hand, and confirm it worked

Do not wait for 03:00 to find out whether it works:

```
launchctl kickstart -k gui/$(id -u)/dev.floyda.ntsb-record
```

This is also the moment the `pinentry-mac` dialog may appear (stage 2) — if it does, decide
then whether to tick "Save in Keychain."

**Check it ran**, two ways:

```
tail data/recorder.log
```

Look for the line `run done` (from the wrapper) after a block of lines starting
`... INFO ntsb_probable_cause.recorder ...` (from the recorder itself, spec §9.1's own log
format) ending in `run done cases=... changed=... new_docs=... failed=... minutes=...`. If you
instead see `NTSB key unavailable` or `run failed exit=...`, the key or the run itself is the
problem — nothing was written to the store beyond stage 4's note above.

```
sqlite3 data/recorder.sqlite "select run_id, started_at, finished_at from runs order by run_id desc limit 3"
```

Each row is one night. `finished_at` set (not blank) means that run completed; a row with no
`finished_at` is one that started and then failed or was interrupted — stage 4 explains why
that is not a data loss on the bridge.

## Stage 7 — After the merge: point the bridge at the main checkout

Once this stage's pull request is merged to `main`, the worktree in stage 1 is no longer where
the current code lives. Edit the plist's first `ProgramArguments` string (the code directory)
from the worktree path to:

```
/Users/floyda/Workspace/ntsb-demo-agent/ntsb-probable-cause
```

then reload it:

```
launchctl bootout gui/$(id -u)/dev.floyda.ntsb-record
launchctl bootstrap gui/$(id -u) ~/Library/LaunchAgents/dev.floyda.ntsb-record.plist
```

The store and log paths do not change — they were already the main checkout's `data/`
directory (stage 1).

---

## Stage 8 — Retiring the bridge, once AWS takes over

When `docs/runbooks/recorder-deploy.md` has the AWS schedule running its own first successful
night, two steps close out the bridge:

**1. Unload the `launchd` job**, so it stops running:

```
launchctl bootout gui/$(id -u)/dev.floyda.ntsb-record
```

(`rm ~/Library/LaunchAgents/dev.floyda.ntsb-record.plist` afterwards if you want it gone for
good, not just stopped.)

**2. Upload everything the bridge has recorded so far, once**, so AWS continues from where the
bridge left off rather than starting empty:

```
aws s3 cp data/recorder.sqlite s3://<bucket>/recorder.sqlite --profile ntsb
```

(`<bucket>` is the name `cdk deploy` printed when the AWS stack was created — see
`docs/runbooks/recorder-deploy.md`.) Do this once, right after unloading the bridge and before
the first AWS run, so exactly one of the two is ever writing to the store at a time.

## Glossary

**`launchd`.** macOS's own job scheduler — the thing that runs a program at a set time, even
across reboots, without you needing to leave a terminal open.

**`plist`** ("property list"). The XML file that tells `launchd` what to run and when — one
file per job, kept in `~/Library/LaunchAgents/` for jobs that run as you (rather than as the
system).

**`pass`.** A command-line password manager. Stores each secret as a small file encrypted with
GPG; `pass show <name>` decrypts and prints one back.

**GPG agent.** A background program that holds your GPG passphrase in memory for a while after
you type it once, so you are not asked again on every use — this is what makes the passphrase
"cached" in stage 2.

**`pinentry`.** The small program the GPG agent calls to ask you for your passphrase.
`pinentry-mac` is the macOS version, which can show a "Save in Keychain" option.

**Worktree.** A second checkout of the same git repository, on a different branch, sharing the
same underlying history — used here so this stage's code can run without touching your main
checkout.

**Interval.** The gap between two observations of the same case (last seen without something,
first seen with it) — the unit the recorder actually measures in, rather than an exact
date. A missed night makes an interval wider; it never invents a wrong date.
